# DECISIONS.md — assumptions made where the spec was silent

Every entry below is a call made while building RouteIQ that the specification did not pin down (or pinned down loosely). Each one is reversible; none changes the `OptimizeRequest → OptimizeResponse` contract.

## Stack & tooling

1. **Next.js 16.3.1 (App Router, Turbopack), React 19.2, Tailwind CSS 4.** The spec says "Next.js 14+"; `create-next-app@latest` produced 16.3.1. Tailwind 4 has no `tailwind.config.js` — theme tokens live in `src/app/globals.css` (`@theme`). Route `params` are Promises in Next 16 (`await params` / `use(params)`).
2. **pnpm 9** as the package manager (`packageManager` field in `package.json`). `npm install` also works.
3. **Vitest 4** for the unit tests (`tests/**/*.test.ts`, node environment, `@/*` alias): optimizer invariants, time utilities, the zustand store (persistence, cross-tab sync, actions — run against a fake `window`, no jsdom), the `/api/*` route handlers (called as plain functions with a `Request`) and the polyline decoder. No component-test framework was added (the spec asked to keep testing light). End-to-end coverage is a **puppeteer-core smoke harness** — `scripts/smoke-e2e.mjs`, run with `pnpm smoke` against a running `pnpm build && pnpm start` and a local Chrome/Edge (or `CHROME_PATH`); it walks the acceptance criteria at 375×812 and 1366×850 (56 checks: markers within 2 s of navigation start, optimize, reassign, driver flow incl. reload persistence, the proof-of-delivery sheet, a failed attempt with a note, "Skip for now", the activity log, the end-of-day report, a driver who arrives before anyone optimized (the route prepares itself), double-tap guard, two-tab sync, route complete, done stops immovable, legend/export/reset, API 400s incl. schema bounds, real 404s, network allow-list = own origin + OSM tiles, no console errors) and writes screenshots to the git-ignored `e2e-screens/`; the curated set lives in `docs/screenshots/`. `puppeteer-core` downloads no browser, so the harness costs nothing on install.
4. **No shadcn/ui.** All shared components are hand-written Tailwind (`src/components/ui`). Fewer moving parts, no CLI-generated files.
5. **ESLint** = `eslint-config-next` (core-web-vitals + typescript). Next 16 no longer runs ESLint inside `next build` — the build gates **TypeScript only** — so `pnpm lint` is `eslint . --max-warnings=0` (warnings fail) and `pnpm verify` (`typecheck && lint && test`) is the real pre-push gate; run it before `pnpm build`. Prettier config (`.prettierrc`) is present for consistency but not enforced by a script.
6. **Line endings** are normalized to LF via `.gitattributes` (the build machine is Windows).

## Optimizer (`nn-2opt-v1`)

10. **Distance model**: every kilometre the optimizer plans with **and reports** is an *estimated road km* = haversine km × **1.3 road factor** (`estimatedRoadKm()` in `distance.ts`); drive time = road km / `avgSpeedKmh` (default 32) × 60. `RouteLeg.distanceKm`, `Route.totalDistanceKm` and `RouteMetrics.totalDistanceKm` are that road estimate rounded to 2 decimals (an earlier build reported raw straight-line km while timing with the factor, which under-stated distances by ~23 %). Baseline and optimized routes use the identical model, so the before/after comparison is apples-to-apples; a router-backed solver reporting real road km is compared against this ×1.3 estimate (roughly like-for-like — see `docs/ALGORITHM_INTEGRATION.md` §6). The k-means assignment compares raw haversine distances internally (the factor cancels).
11. **Assignment**: k-means with k = drivers, centroids seeded by splitting stops into k angular sectors around the depot; ≤ 20 iterations; deterministic (no randomness). Rebalance pass enforces `capacityPackages` (hard) and, when `balanceLoad`, a max stop-count spread of 3 by moving boundary stops. When a cluster is over capacity and nothing fits elsewhere it drops its farthest member **that carries packages** (a 0-package stop frees nothing), and a re-admit pass then retries every dropped stop against the freed room, so only stops that fit nowhere become `unassignedStopIds`.
12. **Sequencing**: nearest-neighbour from the depot then 2-opt on the closed tour (depot → … → depot) until no improvement (capped at 500 passes for safety).
13. **Time windows**: arriving *before* a window opens means the driver **waits** — the ETA is clamped to the window start and the wait counts toward route time; this is **not** a violation. A violation is an arrival (rounded to the displayed minute) **strictly after** the window end. The repair pass (`repair.ts`) works within one driver's route (never across drivers) and alternates two local-search passes until neither changes anything: a **late pass** that moves a late stop *earlier* and keeps a move only if it reduces the violation count (ties broken by distance), and an **idle pass** that, while some stop waits for its window to open, tries every single-stop relocation (push the waiting stop later *or* pull a stop from behind the wait forward) and keeps the best move that does not add violations and gets the driver back to the depot strictly earlier — or equally early with a strictly lower sum of arrival times. Without the idle pass a distance-only order visited the 13:00–15:00 stops at 09:20 and parked the driver for hours mid-route (seed: 1136 → 1051 total minutes, longest route 408 → 393 min after adding it); now the remaining wait sits at the route tails and every no-window stop is delivered in the morning. Caps: 100 iterations per pass, 20 alternations, idle pass only for routes ≤ 120 stops, late pass only for routes ≤ 300 stops, and a **1.5 s wall-clock budget per request** shared by all drivers (`REPAIR_TIME_BUDGET_MS`) — without it a schema-valid 1000-stop request with many late windows ran the late pass for minutes (measured 41 s over HTTP / 247 s in-process before the cap; ~9 s → bounded now). Deterministic (fixed scan order, explicit tie-breaks) whenever the budget is not hit, i.e. for anything but pathological inputs. Skipped entirely when `respectTimeWindows === false` — ETAs still wait for windows and metrics still count violations in that case.
14. **`etaByStopId`** is the arrival time after any wait; departure = arrival + `serviceMinutes`. ETAs are `"HH:MM"` on the shift day's clock and **do not wrap at midnight** (`"25:13"`, GTFS-style; rendered `1:13 AM +1`): an earlier build wrapped them mod 24 h, which made ETAs non-monotonic and let `computeMetrics` (which re-derives violations from the strings) count a next-day `"09:05"` as inside a `09:00–11:00` window — a 31-hour, 300-stop test route reported 55 violations instead of 100. `Route.totalMinutes` = arrival back at depot − `shiftStart` (drive + service + wait). Per-leg `driveMinutes` are integer-rounded for display; totals use unrounded values, so summing legs can differ from `totalMinutes` by a minute.
15. **Metrics**: `totalDistanceKm` = Σ route km, `totalMinutes` = Σ route minutes, `longestRouteMinutes` = max, `timeWindowViolations` = count of late stops. `stopsPerDriver` keyed by driver id.
16. **Baseline** (`baseline-round-robin-v1`) = stops in file order dealt round-robin to drivers, no sequencing, no capacity check (it represents "what dispatch does today"), scheduled with the same distance model as #10. Zero drivers → everything unassigned. On the seed: 355.4 km / 20 h 24 m / longest 9 h 25 m / 6 violations, versus 174.8 km / 17 h 31 m / 6 h 33 m / 0 after `nn-2opt-v1` (−51 % km, −14 % time).
17. **`computeMs`** is reported with one decimal (e.g. `44.1`), measured with `performance.now()`. The placeholder takes a few tens of milliseconds on the seed (~25–90 ms depending on machine and warm-up; ~3 ms without the idle-repair pass), well inside the 2 s budget.
18. `optimize()` and `baseline()` are pure, dependency-free TypeScript so they run identically in the Route Handler and in the browser (used as an offline fallback — see 22).

## API

19. `POST /api/optimize` validates with **zod 4**; unknown keys are stripped rather than rejected; invalid input → `400 { error, issues: [{ path, message }] }`; malformed JSON → `400` with an empty `issues` list; an optimizer exception → `500`. Because the endpoint is public and the placeholder is O(n²)–O(n³), the schema also **caps a request at 1000 stops and 50 drivers**, bounds the numeric fields (`avgSpeedKmh` 1–200, `serviceMinutes` ≤ 1440, `packages` ≤ 10 000, `capacityPackages` ≤ 1 000 000, `color` must be a hex colour — `avgSpeedKmh: 5e-324` used to produce a 500 / `NaN:NaN` ETAs), rejects time windows whose `end` is before `start`, rejects **duplicate stop ids / duplicate driver ids** (issue path `stops` / `drivers`, message lists the offenders) and rejects a stop whose id is the reserved literal `"DEPOT"` (path `stops.<i>.id`). All three routes set `runtime = 'nodejs'` and `dynamic = 'force-dynamic'`; `/api/seed` and the optimize response send `Cache-Control: no-store`.
20. `/api/health` reports `version: '1.0.0'` (hard-coded; bump alongside `package.json`).

## State & persistence

21. Zustand store persisted under **`routeiq-v1`** (blob `version: 1`). Persisted: depot, drivers, stops (incl. statuses **and proof of delivery**), routes, both metrics, algorithm, computeMs, lastOptimizedAt, editedSinceOptimize, activeDriverId, hiddenDriverIds, deliveryLog. Not persisted: selectedStopId, toast, isOptimizing, optimizeError, hasHydrated. Version-0 blobs (an earlier build, straight-line km) are **migrated**: data, delivery progress and prefs are kept, the plan (routes/metrics/algorithm/computeMs/lastOptimizedAt) is dropped so the user re-optimizes once. Pages render skeletons until `useHasHydrated()` is true (avoids hydration mismatches); that hook reads a module-level flag set by `onRehydrateStorage` in **both** the success and the error branch, so a failed rehydration can never leave a page on its skeleton.
    - **Resilient storage.** The store uses a small custom `PersistStorage` instead of `createJSONStorage`: every `localStorage` access is wrapped in try/catch (Safari "block all cookies", sandboxed iframes, quota errors → the app runs in memory), an unparsable or mis-shaped blob is discarded with a `console.warn` and the app boots with defaults, and each persisted key is shape-checked on read (`pickPersisted`) so a bad `stops` value falls back to its default instead of crashing a selector.
    - **Write dedupe + cross-tab sync.** zustand re-serialises the persisted slice on *every* `set`, including ephemeral-only ones (toast, selection). The storage wrapper skips writes whose blob is byte-identical to what it last read/wrote/saw, so a dispatcher tab that only shows a toast never overwrites the progress a driver tab persisted meanwhile; and a `storage` event listener applies another tab's persisted slice (stops/routes/metrics/activeDriverId/hiddenDriverIds/deliveryLog — never the ephemeral keys, never the hydration flag) straight into the open tab, so /dispatch and /driver on the same device stay consistent instead of clobbering each other. Every persisted key is shape-guarded on the way in, `deliveryLog` included (entries without an id / timestamp / stop id / type are dropped rather than rendered as blank rows).
22. **`optimize()` calls `POST /api/optimize`** (the swap seam) and only if that request fails or returns a malformed body does it fall back to the local `optimize()` with a `console.warn`. Baseline metrics are always computed locally (pure function). This keeps the demo working offline / behind a flaky network without hiding the API seam. The only callers are the **Optimize / Re-optimize routes** button on `/dispatch` and `/driver/[id]`, which **prepares a plan automatically** when it opens and finds none (see 45) — plus its "Prepare my route" / "Try again" button. Nothing else (not `resetDemo`, not a status change, not a status-changing driver action, not the picker) triggers the algorithm.
23. **Manual reassignment** (`moveStop`) rewrites the `driverId → stopIds[]` map and re-runs **only `schedule()`** — ETAs and metrics update synchronously; baseline metrics are left untouched (they are the "before"). It also works **before any optimisation**: the first move bootstraps an empty plan (every driver `[]`), so "Reassign to…" in a map popup creates a one-stop route while `algorithm` / `lastOptimizedAt` / `baselineMetrics` stay null. `moveStop` returns a boolean — `false` for a no-op (dropped where it already was), an unknown stop / driver, no depot, or a **delivered / failed stop** (a done stop stays with the driver who did it; moving it would credit another driver and pad their ETAs — the ⋯ menu, drag handle and map-popup select are disabled for done stops too) — and every caller (map popup, ⋯ menu, drag-and-drop, unassigned list) toasts "Moved …" **only when it returns `true`**. A real move sets `editedSinceOptimize`, which the panel header shows as "· edited by hand" (or "Assigned by hand · not yet optimized" before the first optimisation, where the button also says "Optimize", not "Re-optimize"); optimising or resetting clears it.
24. **Stop status changes do not re-plan.** Marking a stop delivered/failed only updates the stop; ETAs stay as planned. `deliveredAt` is set for both `delivered` and `failed` (attempt time) and cleared when reverted to `pending`.
25. **Failure reasons** are stored in the existing `notes` field as `"<reason> · <original notes>"` (no schema change); re-failing with another reason replaces the prefix instead of stacking. **Reverting to `pending` (undo) strips the reason prefix again** so a mis-tap leaves no trace and the Next Stop card never shows "No one home" as if it were a delivery instruction; while a stop is `failed` the driver's details sheet shows the reason as "Last attempt: …" and only the free-text remainder as notes.
26. `resetDemo()` reloads the bundled seed (fresh statuses; no network — see #57), clears routes/metrics/legend toggles, keeps `activeDriverId`, and does **not** re-optimize.

## Map

27. **Precomputed road paths (optional §4.4) were implemented.** `scripts/precompute-paths.ts` fetched, once, the OSRM demo-server driving polylines for all 1,035 unordered pairs of seed points and stored them Google-encoded in `src/data/paths.json` (~96 KB, loaded only by the lazily imported map chunk). The map uses them purely for **drawing**; distances/ETAs remain the haversine × 1.3 model (#10) so the optimizer contract stays independent of any external routing data — the km on screen are that road *estimate*, not the length of the drawn polyline. Paths are assumed symmetric (reversed for the opposite direction). The app never calls OSRM at runtime; if a pair is missing (e.g. a non-seed stop) the leg is drawn as a straight line.
28. Markers are Leaflet `divIcon`s (no image assets): 28 px coloured pins with the sequence number when routed (number colour picked by `onColor()` — slate-900 on the orange/green drivers, white on blue — so it always meets AA), amber/violet dots for priority/overnight, a green check for delivered, red X for failed, ring for selected; depot is a 32 px slate square. Route lines get a white halo for contrast, and small direction arrows on legs longer than ~700 m (≤ 60 arrows total). Zoom control sits top-right so the mobile bottom sheet never covers it; on phones the OSM attribution is CSS-ordered *above* the zoom bar in that corner so the opened legend never overlaps it. Attribution is the OSM-required string. A selected stop's popup pans into the part of the map not covered by the bottom sheet (`MapView.viewportInset`).
29. In the driver view the "current position" is the previous stop (or the depot before the first stop) — no geolocation is used (spec).

## Dispatcher UX

30. Mobile: full-screen map + bottom sheet with `peek` / `half` / `full` snaps (drag handle with a 44 px hit area, velocity-biased snapping, `100dvh`; the peek height and the header padding include `env(safe-area-inset-bottom)` so the Optimize button clears the home indicator, and the sheet body is `inert` while peeking so hidden rows are not in the tab order). Desktop (≥ 768 px): map left, panel right at `clamp(340px, 40vw, 460px)` so the map keeps ≥ ~56 % of a 768 px screen.
31. Cross-driver moves: **desktop** drag-and-drop with `@dnd-kit` (pointer + keyboard sensors; pointer drops use `pointerWithin`, so releasing over the map / header / a gap **cancels** instead of dropping on the nearest route, and dropping a row on its own card's padding is a cancel too; the insertion line is drawn above or below the hovered row from the pointer position and the drop uses the same side); **mobile** uses the per-row "⋯ → Move to Driver X" menu (spec: drag on a touch bottom sheet is fiddly; the menu measures itself after mounting and flips/scrolls so it never overlaps its trigger or leaves the viewport, and keyboard focus follows the moved row to its new card). The map popup also offers a "Reassign to…" select on both.
32. "Reset demo" uses an inline confirm (no `window.confirm`, which would block browser automation and looks off-brand). "Export routes (JSON)" downloads a self-contained `{ exportedAt, algorithm, optimizedAt, depot, drivers, stops, routes, unassignedStopIds, metrics, baselineMetrics }` — the stops are included so every id in `routes` resolves, and unassigned stops are listed explicitly (an earlier build exported routes + metrics only).
33. Legend (per-driver show/hide) is a collapsible chip on mobile so it doesn't crowd a 375 px map. Hidden drivers are shown struck-through in slate-500 (AA) rather than faded.
34. **Toasts are rendered per screen, not in the root layout.** `<Toast bottomOffset={…}>` sits in `DispatchScreen` (offset = the sheet's peek height on phones, so it floats above the Optimize strip) and in the driver screens (offset = the 56 px bottom bar), each adding `env(safe-area-inset-bottom)` itself. This keeps the landing page free of the store bundle and stops the toast covering the primary action.

## Driver UX

35. Failure reasons: `No one home` / `Wrong address` / `Damaged` / `Other`, chosen in a small modal sheet (focus lands on the sheet **panel itself**, not on the first reason and not on the first focusable control, so a held Enter on "Failed" cannot record a failure by key-repeat — see #37 for why "the first focusable control" was the wrong fallback). The Next Stop card ignores Delivered / Failed presses in its **first 400 ms** (`ACTION_SETTLE_MS`): it is keyed on the stop id, so after a tap the next stop's card mounts under the finger with identical buttons and an accidental double-tap marked two stops. "Navigate" opens the Google Maps directions deep link in a new tab (allowed by spec — no API key). "Return to depot" appears after the last stop and deep-links to the depot.
36. `/driver` remembers the last chosen driver (`activeDriverId`) and highlights it. `/driver/[id]` claims it **once per mount** by reading the store imperatively — not in an effect that reacts to `activeDriverId`: that value is cross-tab-synced, and the reactive version made two driver tabs (D1 and D2) overwrite each other ~30 times a second, forever. Unknown ids are a real 404 (`notFound()` from the server page; `src/app/not-found.tsx` / `error.tsx` exist app-wide) rather than a 200 with a client-side message.
37. Driver sheets (stop details, failure reason, proof of delivery, activity log) are **native `<dialog>` elements opened with `showModal()`** — top layer, background inert for pointer/keyboard/AT, Escape via the `cancel` event — with a `position: fixed` body scroll lock that survives iOS. Two focus details are load-bearing. **A sheet with no `[data-autofocus]` focuses the panel, never "the first focusable control"**: that fallback resolved to the ✕ Close button, so a held Enter on the card's "Delivered" auto-repeated onto Close and the proof sheet vanished with nothing recorded — the exact key-repeat accident #35 exists to prevent, one element to the left. And the cleanup **calls `dialog.close()` before restoring focus**: removing an open modal from the DOM does drop it from the top layer, but under StrictMode the effect's second run then captures an element *inside* the still-open dialog as "previously focused", and closing the sheet dropped focus to `<body>` instead of returning it to the button that opened it. After Delivered/Failed from the Next Stop card, keyboard focus moves to the new card's heading (or "Route complete") instead of dropping to `<body>`; the stop list deliberately does **not** auto-scroll on completion (the Next Stop card at the top is the source of truth). Done rows are dimmed by colour + strike-through rather than opacity so every text run stays ≥ 4.5:1.

### Sign-in, delivery records, log and report

(Separate list so the numbering continues at 45 rather than restarting inside the section above.)

45. **A driver never waits for dispatch.** Opening `/driver/[id]` with no plan used to be a dead end ("Routes not optimized yet — ask dispatch" + an "Optimize now (demo)" button). The screen now **prepares the plan itself**: one `optimize()` call on mount, a "Preparing your route…" state (spinner + the silhouette of the card that is coming) while it runs, and a "Try again" button if it fails. Exactly one automatic attempt per mount, and only when the screen *arrived* with no plan — captured by adjusting state during the first hydrated render (`planAtFirstLook`, the same "derive from an incoming value" pattern `Toast` uses), never in an effect and never from a ref, which the React Compiler lint rules forbid in render. Why "arrived with none" and not "has none": if a plan existed and then vanished, the dispatcher pressed **Reset demo**, and silently re-optimizing would undo their reset from under them (with two tabs open it also raced the reset). That case shows "Your route was cleared · Prepare my route" instead — one tap, driver's choice. The driver's `optimize()` passes `{ toast: 'driver' }`: the dispatcher's headline toast ("Optimized in 70 ms · nn-2opt-v1") is the point of the demo on `/dispatch` and gibberish on a phone that quietly planned its own day, so the driver gets **"Your route is ready"**. `optimize()` with no argument is unchanged, and `{ toast: 'none' }` is silent; failures still toast in every mode except `none`. The picker (`/driver`) says the same thing ("pick your name and today's route is prepared for you") and shows per-driver stop count, next ETA, planned duration, a progress bar with "x of N done" / "Route complete", and a **Continue** button on the last-used driver.
46. **Proof of delivery** (`Stop.proof`, additive and optional so old persisted blobs still load): `method` (`handed` / `door` / `neighbour` / `desk`), `recipientName`, `note`, `photo`, `at`. Tapping **Delivered** opens a compact sheet with the four methods as a radio group — `handed` pre-selected — optional recipient (prefilled with `stop.recipient`), optional note, optional photo, and one big **Confirm delivery**. The common path stays **two taps** (Delivered → Confirm). Like the fail sheet, nothing is auto-focused (focus goes to the panel, #37), so a held Enter on "Delivered" cannot confirm a delivery — or dismiss the sheet — by key repeat, and the Next Stop card keeps its 400 ms settle window (`ACTION_SETTLE_MS`). The recipient field is a **prefill only until it is touched**: picking "Left at door" clears the planned name (a parcel on a doorstep was handed to nobody) and coming back to "Handed to recipient" restores it, but once the driver has typed in the field — including deliberately emptying it — the method never rewrites it again. A failed attempt keeps the reason-in-notes mechanism (#25) and may now carry a free-text note, typed *above* the reason buttons so picking a reason is still a single tap; marking a stop failed also **clears any `proof` an earlier delivery of that stop left behind**, so a failed stop can never show "Handed to recipient" and a photo of a parcel that is back in the van.
47. **Photos are 320 px thumbnails, never the camera frame.** `<input type="file" accept="image/*" capture="environment">` → canvas downscale (longest side ≤ 320 px, JPEG q 0.7, ~15–40 KB; EXIF orientation honoured via `createImageBitmap(..., { imageOrientation: 'from-image' })` with an `<img>` fallback). The whole app state lives in one ~5 MB localStorage key, so a 3 MB frame (≈ 4 MB base64) would blow the budget on the first stop. A per-origin **photo budget** (`PHOTO_BUDGET_BYTES`, 1.5 MB) is checked before storing: over it the delivery is still recorded, only the picture is dropped, and the toast says so ("photo not saved — the photo budget for this device is full"; not "storage full", which reads like the phone is out of space). Budget and UI measure the same thing — `storedPhotoBytes()`, the **length of the data URL**, which is what the persisted blob actually carries; the sheet used to print the *decoded* size (~1.34× smaller), so "Photo attached · 28 KB" and a full budget looked like they were about different pictures. A photo that cannot be decoded never blocks the record.
48. **Append-only activity log** (`deliveryLog`, persisted, capped at `MAX_LOG_EVENTS` = 2000 with the oldest dropped). Every driver action appends exactly one `DeliveryEvent` (`delivered` / `failed` / `undo` / `deferred`) through a store action — `recordDelivery` / `recordFailure` / `undoStop` / `deferStop` — so components never build events by hand; `setStopStatus` stays the low-level primitive. Events are **denormalised** (they copy the outcome, method and reason) so the log still reads correctly after a re-optimisation or an undo, and they carry `hasPhoto` rather than the image (which lives once, on the stop). A row therefore only shows a thumbnail when the event **is** the stop's standing outcome (`event.at === stop.proof.at`): the image belongs to the stop, so after undo + re-delivery with a different photo the older row would otherwise illustrate itself with the newer picture. An `undo` cancels the standing outcome for its stop when the day is summarised, so a corrected mis-tap does not inflate the numbers. The log is reachable in one tap from the route header and is cleared by **Reset demo** (the statuses it describes are cleared too). Two things keep it honest. It is scoped to **the local calendar day** (`eventsForDriver(log, driverId, route, now)`): the log is append-only and persisted, so on a device nobody reset, yesterday's events kept counting into "N entries today", the header count and — worst — `summarizeDay().actualMinutes`, which is first-to-last event and would have read "27h 10m"; older events stay in storage, they are simply not today. And the persisted-blob guard checks `type` against the **known set** (`delivered|failed|undo|deferred`), not just `typeof === 'string'`: one event with an unrecognised type reached the log sheet, where `TYPE_META[type].badge` threw and took the whole `/driver/[id]` screen down *on load* — and "Try again" re-crashed, because the blob is persisted. Unknown types are refused at the door (all-or-nothing per key, like every other persisted key) and the sheet also skips a row it cannot render.
49. **"Skip for now"** moves a still-pending stop to the **end of the same driver's route** and re-runs `schedule()` — the same reorder-and-reschedule as a dispatcher's manual move (#23), so ETAs and metrics stay consistent, but deliberately **without** `editedSinceOptimize`: a driver skipping their own stop is not a dispatcher editing the plan, and the panel claiming "edited by hand" hides whether the dispatcher's own edits are still in place. Both callers share one pure `planAfterMove()` helper and differ only in that bookkeeping. It is deliberately quiet (a ghost button under Navigate, plus a row in the stop-details sheet) so the two outcome buttons stay the obvious choice, it is hidden when only one stop is left, and it is a no-op (with an explanatory toast) when the stop is already last. There is no "unskip": the log records the skip, and the driver can deliver the stop from the list at any time.
50. **Undo lives in the toast.** `showToast` takes an optional `{ label, onAction }`; the delivered / failed toasts use it for **Undo**, which reverts the stop to pending, strips the proof (and the reason prefix, #25), appends an `undo` event and moves focus to the restored card. The toast keeps its dismiss button and stays inside the existing `role="status"` live region.
51. **End-of-day report.** The Route complete card reports delivered / failed / skipped, packages delivered, **actual time on route** (first → last recorded event) next to the planned duration, and planned distance — and downloads two files: `routeiq-report-<driver>-<date>.csv` (one row per stop in route order — seq, address, recipient, packages, planned ETA, outcome, timestamp, method or reason, recipient name, note; pending stops get a row too, so the CSV is a full manifest) and `routeiq-events-<driver>-<date>.json` (driver, route, summary and the raw event stream). Three things about the CSV are deliberate, and all three are about the spreadsheet that opens it. **CRLF**, because Excel reads an LF-only file as a single row. **A UTF-8 BOM** (`downloadText` prepends it for `text/csv` only — `JSON.parse` rejects one), because Excel on Windows opens a BOM-less UTF-8 file as CP-1252 and turns every accented address or name into mojibake. And **the timestamp is emitted twice**, `at (local YYYY-MM-DD HH:MM)` next to `atIso (UTC)` with the units named in the header row: the single UTC column sat beside a *local* `plannedEta` and made every delivery look hours late. Free-text fields are also neutralised against **formula injection** — a leading `= + - @ TAB CR` gets a `'` prefix — because a driver's note goes straight into the depot's Excel, where `=HYPERLINK("http://evil","Click")` would otherwise be a live link. The `downloadText` helper moved out of `DispatchActions` into `src/lib/download.ts` and both screens import it.

38. Manifest is generated by `src/app/manifest.ts` (served at `/manifest.webmanifest`); icons 192/512 (+ 180 apple-touch) are PNGs produced by `scripts/generate-icons.mjs` (`pnpm generate-icons`), a dependency-free Node script. ## Performance (Lighthouse mobile)

42. **What was done for load performance.** The Leaflet chunk (`MapViewInner`) is preloaded the moment a map page's JS evaluates (parallel with hydration); the map is created directly on its final bounds (`MapContainer bounds`, no throw-away default-zoom tiles); the 45 markers and polylines are streamed in with `useDeferredValue` (time-sliced transition, so the tiles paint before the marker commit); `<link rel="preconnect">` to `tile.openstreetmap.org`; no `Intl`/`toLocale*` calls on the hot path (the first `Intl.DateTimeFormat` cost ~180 ms on a mid-range profile — dates and clock times are hand-formatted); no synchronous layout reads during mount (header height comes from `ResizeObserver` entries, viewport height / safe-area inset are read in a `requestAnimationFrame` and via a `:root` custom property instead of a probe element); the map wrapper is `relative z-0 isolate` so Leaflet's z-indexes never trigger extra stacking work.
43. **Map loading placeholder is an image, deliberately.** While the Leaflet bundle loads, `MapSkeleton` shows `public/map-placeholder.webp` — a 6 KB, slate-toned, abstract silhouette of Madison's isthmus generated by `scripts/generate-map-placeholder.mjs` (SVG drawn procedurally, rasterised with a local Chrome; no OSM data). It reads as "a map is coming" instead of a grey block, ships in the server-rendered HTML with `fetchpriority="high"` + `decoding="sync"` so it joins the first paint, and — being the largest element on a phone — it is the page's Largest Contentful Paint candidate rather than a map tile that can only appear after Leaflet boots. A raster (not the SVG) is used because an SVG in an `<img>` is painted on the main thread, which is busy booting the app on slow devices. Preloading the first map tiles was tried and rejected: on a slow-4G budget the ~150 KB of tiles compete with the JS and make everything later.
44. **Measured numbers (honest caveat).** Lighthouse 12, mobile preset, against `pnpm build && pnpm start` on the Windows dev laptop that built this (Lighthouse itself warns *"The tested device appears to have a slower CPU than Lighthouse expects"*, benchmark index ≈ 650–900 vs the ≈ 1500 its 4× throttle assumes), medians of three runs: **landing** perf 89 / a11y 100 / best-practices 100 / SEO 100; **/driver/D1** perf 67 / a11y 100 / 100 / 100; **/dispatch** perf 54 / a11y 96 / 96 / 100 (accessibility 96 because Leaflet's 28 px stop markers overlap each other in dense clusters — the target-size audit — the same content is reachable from the panel list with 44 px rows). With the CPU multiplier calibrated to this machine per Lighthouse's own guidance (`--throttling.cpuSlowdownMultiplier=2`): landing 98, driver 79, dispatch 71. On `/dispatch` the remaining gap is the map itself: Lighthouse's Lantern model measures LCP from a localhost run in which the JS arrives with the HTML, so the first painted frame already contains the Leaflet map and the LCP becomes the first OSM tile (~4 s on simulated slow 4G); on a deployed origin the placeholder paints first. PWA installability (manifest with any + maskable icons, service worker in production, standalone display) is in place. Re-run locally with `pnpm dlx lighthouse http://localhost:3000/dispatch --form-factor=mobile --screenEmulation.mobile --chrome-flags=--headless=new`.
52. **Road geometry loads only when a route is drawn.** `src/data/paths.json` is 96 KB — a quarter of everything the map downloads — and nothing needs it until there is a plan on screen. A static import put it in the Leaflet chunk group, so every first visit to `/dispatch` paid for geometry it never drew. `mapMath` now pulls it in with a dynamic `import('@/data/paths')` (`loadRoadPaths()`), and `RoutePolyline` renders nothing until that resolves rather than flashing straight lines that snap to roads a frame later; a failed load falls back to straight legs. `src/data/paths.ts` itself is unchanged and still synchronous, so the tests and any server-side caller keep their contract. Effect: a fresh `/dispatch` downloads **97 KB less JavaScript** (914 KB → 777 KB total, with the dnd-kit split below); a page that does draw routes fetches the same bytes, just after the tiles instead of alongside them.
53. **dnd-kit is desktop-only, so phones never download it.** Drag & drop between driver cards only exists on md+ (phones move stops with the ⋯ menu), but `@dnd-kit/core` + `sortable` + `utilities` (~48 KB) sat in the dispatcher's critical chunk on every device. `DriverRoutes` now owns the markup for both viewports and splices the drag pieces in through a `DragSlots` object (`src/components/dispatch/dragSlots.ts`); `DriverRoutesDnd` — the only module that imports dnd-kit — is loaded with `React.lazy` on desktop, with the non-draggable cards as the Suspense fallback so the panel is readable and the ⋯ menus work from the first paint. Effect: −48 KB of critical JS on a phone's `/dispatch`, and −47 KB of link-prefetch on `/` and `/driver` (which prefetch the dispatcher's bundle).
54. **The stylesheet ships inside the HTML (`experimental.inlineCss`).** Tailwind produces one ~46 KB atomic sheet that every page must have before it can paint, and the browser only discovers it after parsing the HTML — behind the script preloads in the request queue. Inlining removes that render-blocking round trip. Measured on a simulated slow-4G phone (4× CPU, 150 ms RTT, 1.6 Mbps; medians of 5–7 interleaved runs) it took **first contentful paint on `/` from 4.3 s to 3.3 s** (and 3.24 s → 1.68 s on a quiet machine), and was neutral on `/dispatch`. The cost is ~28 KB more HTML per page, because Next serialises the inlined sheet into the RSC flight payload as well as the `<style>` tag; a demo people open once trades that for the round trip. It is a loss on `/driver/[id]` only because that screen's skeleton paints nothing at all until JavaScript runs (see #48).
55. **Other load-path changes, and what was tried and dropped.** The OSM `preconnect`/`dns-prefetch` moved out of the root layout into `MapSkeleton` (via React 19's `preconnect()`, which hoists the tag into `<head>` during SSR), so the landing page and the driver picker — which never show a map — no longer open a TLS connection they will not use. The service worker enables **navigation preload**, so a repeat visit's HTML request starts in parallel with waking the worker instead of after it. `poweredByHeader: false`. Rejected after measuring: **`reactCompiler: true`** — build time went from 3.1 s to 55 s for no measurable runtime win (the components here are already hand-memoised and the blocking time is react-dom's own evaluation, not app re-renders); **caching `/_next/static/*` in the service worker** — those files are already served `immutable` with a year-long max-age, so the HTTP cache does the same job without the risk of a worker serving a stale shell; **preloading map tiles** (already rejected in #43).

56. **Where the numbers landed, and the one page that got worse.** One interleaved Lighthouse 12 A/B (mobile preset, the same commit before and after, both servers up at once so machine drift hits both): `/` 90 → 92 (speed index 3.09 s → 0.91 s, first paint 1.40 s → 0.91 s), `/driver` 92 → 96 (blocking time 174 → 92 ms), **`/dispatch` 52 → 70** (LCP 6.21 s → 4.15 s, blocking time 1238 → 608 ms, JS 897 → 777 KB) — and `/driver/[id]` **83 → 74**, the one regression. Two causes, both nameable: that screen is the only one whose server-rendered skeleton has no text and no image (only `Skeleton` boxes, which are background colours and do not count as a contentful paint), so it cannot paint until its JavaScript has run and it therefore pays for the bigger inlined-CSS document without getting the render-blocking round trip back; and Turbopack re-chunked the map group when the road geometry moved out, which added ~40 KB to that route's total. Dropping `<MapSkeleton />` into `RouteScreenSkeleton` where the map placeholder box is today would fix the first — it is what `DispatchSkeleton` already does and why `/dispatch` paints at 1.5 s. Still on the table and measured but not done here (they live in files owned elsewhere): the store fetches `GET /api/seed` on every cold start even though `getSeed()` is bundled into the same chunk — a whole request in front of the first map frame, for data the browser already has; and `src/lib/optimizer`'s assign/sequence/repair stages (~750 lines) sit in the store's chunk on every page although only `optimize()` needs them, while `schedule()` is the only part a manual move requires.
57. **Follow-ups the orchestrator applied after the A/B above.** (a) `loadSeed()` no longer fetches `/api/seed`: the seed is bundled into the store chunk (`getSeed()`, deep-cloned per call), and both map pages gate their first frame on `depot`, so the round trip — a serverless invocation plus an RTT on a deployed origin — bought nothing; the endpoint stays for API consumers. (b) The store imports only `schedule()` statically and `import()`s the assignment/sequencing/repair stages (+ `baseline`) when the user actually optimizes and the API is down, keeping ~15–20 KB off the boot chunk of `/driver`, `/driver/[id]` and `/dispatch`. That `import()` is allowed to fail on its own terms — a hashed chunk is gone after a redeploy, or the device is offline — so it sits in its own try/catch: a plan the API already returned is kept (only the "before" comparison is missing, `baselineMetrics` is already nullable), and only when there is *also* no API plan does it become the error state ("Optimizer unavailable offline"). Wrapping it in the outer try meant a chunk 404 threw away a good plan. (c) `RouteScreenSkeleton` on `/driver/[id]` embeds `MapSkeleton` (the 6 KB placeholder image) instead of a grey box, so that page has a contentful paint before its JS runs — the fix for the regression in #56; it passes `decorative` so the placeholder's own `role="status"` does not sit inside the skeleton's live region and announce the same wait twice.
