# DECISIONS.md — assumptions made where the spec was silent

Every entry below is a call made while building RouteIQ that the specification did not pin down (or pinned down loosely). Each one is reversible; none changes the `OptimizeRequest → OptimizeResponse` contract.

## Stack & tooling

1. **Next.js 16.3.1 (App Router, Turbopack), React 19.2, Tailwind CSS 4.** The spec says "Next.js 14+"; `create-next-app@latest` produced 16.3.1. Tailwind 4 has no `tailwind.config.js` — theme tokens live in `src/app/globals.css` (`@theme`). Route `params` are Promises in Next 16 (`await params` / `use(params)`).
2. **pnpm 9** as the package manager (`packageManager` field in `package.json`). `npm install` also works.
3. **Vitest 4** for the unit tests (`tests/**/*.test.ts`, node environment, `@/*` alias): optimizer invariants, time utilities, the zustand store (persistence, cross-tab sync, actions — run against a fake `window`, no jsdom), the `/api/*` route handlers (called as plain functions with a `Request`) and the polyline decoder. No component-test framework was added (the spec asked to keep testing light). End-to-end coverage is a **puppeteer-core smoke harness** — `scripts/smoke-e2e.mjs`, run with `pnpm smoke` against a running `pnpm build && pnpm start` and a local Chrome/Edge (or `CHROME_PATH`); it walks the acceptance criteria at 375×812 and 1366×850 (41 checks: markers within 2 s of navigation start, optimize, reassign, driver flow incl. reload persistence, legend/export/reset, API 400s, network allow-list = own origin + OSM tiles, no console errors) and writes screenshots to the git-ignored `e2e-screens/`; the curated set lives in `docs/screenshots/`. `puppeteer-core` downloads no browser, so the harness costs nothing on install.
4. **No shadcn/ui.** All shared components are hand-written Tailwind (`src/components/ui`). Fewer moving parts, no CLI-generated files.
5. **ESLint** = `eslint-config-next` (core-web-vitals + typescript). Next 16 no longer runs ESLint inside `next build` — the build gates **TypeScript only** — so `pnpm lint` is `eslint . --max-warnings=0` (warnings fail) and `pnpm verify` (`typecheck && lint && test`) is the real pre-push gate; run it before `pnpm build`. Prettier config (`.prettierrc`) is present for consistency but not enforced by a script.
6. **Line endings** are normalized to LF via `.gitattributes` (the build machine is Windows).

## Seed data (`src/data/`)

7. **Depot** exactly as suggested: Madison East Station, 4001 Anderson St, 43.1214 / −89.3305.
8. **45 stops** with invented house numbers on real Madison streets, spread over Capitol Square, State St, UW campus, Willy St, Atwood, East Towne, Hilldale/Shorewood, West Towne, Fitchburg edge, Monona, Middleton edge, Tenney Park, Vilas/Monroe St, South Park St and Northport. Priorities: 30 standard / 10 priority / 5 overnight; **13 stops** have time windows (spec: "about 12"); packages total 118 (fits comfortably in 3 × 60 capacity); `serviceMinutes` 2–8. Coordinates are approximate street-level positions (good enough for a demo, not geocoded).
9. Recipient names are fictional; a few stops carry `notes` (dock instructions, fragile, refrigerated) to make the driver UI feel real.

## Optimizer (`nn-2opt-v1`)

10. **Distance model**: every kilometre the optimizer plans with **and reports** is an *estimated road km* = haversine km × **1.3 road factor** (`estimatedRoadKm()` in `distance.ts`); drive time = road km / `avgSpeedKmh` (default 32) × 60. `RouteLeg.distanceKm`, `Route.totalDistanceKm` and `RouteMetrics.totalDistanceKm` are that road estimate rounded to 2 decimals (an earlier build reported raw straight-line km while timing with the factor, which under-stated distances by ~23 %). Baseline and optimized routes use the identical model, so the before/after comparison is apples-to-apples; a router-backed solver reporting real road km is compared against this ×1.3 estimate (roughly like-for-like — see `docs/ALGORITHM_INTEGRATION.md` §6). The k-means assignment compares raw haversine distances internally (the factor cancels).
11. **Assignment**: k-means with k = drivers, centroids seeded by splitting stops into k angular sectors around the depot; ≤ 20 iterations; deterministic (no randomness). Rebalance pass enforces `capacityPackages` (hard) and, when `balanceLoad`, a max stop-count spread of 3 by moving boundary stops. Stops that fit nowhere by capacity become `unassignedStopIds`.
12. **Sequencing**: nearest-neighbour from the depot then 2-opt on the closed tour (depot → … → depot) until no improvement (capped at 500 passes for safety).
13. **Time windows**: arriving *before* a window opens means the driver **waits** — the ETA is clamped to the window start and the wait counts toward route time; this is **not** a violation. A violation is an arrival (rounded to the displayed minute) **strictly after** the window end. The repair pass (`repair.ts`) works within one driver's route (never across drivers) and alternates two local-search passes until neither changes anything: a **late pass** that moves a late stop *earlier* and keeps a move only if it reduces the violation count (ties broken by distance), and an **idle pass** that, while some stop waits for its window to open, tries every single-stop relocation (push the waiting stop later *or* pull a stop from behind the wait forward) and keeps the best move that does not add violations and gets the driver back to the depot strictly earlier — or equally early with a strictly lower sum of arrival times. Without the idle pass a distance-only order visited the 13:00–15:00 stops at 09:20 and parked the driver for hours mid-route (seed: 1136 → 1051 total minutes, longest route 408 → 393 min after adding it); now the remaining wait sits at the route tails and every no-window stop is delivered in the morning. Caps: 100 iterations per pass, 20 alternations, idle pass only for routes ≤ 120 stops. Deterministic (fixed scan order, explicit tie-breaks). Skipped entirely when `respectTimeWindows === false` — ETAs still wait for windows and metrics still count violations in that case.
14. **`etaByStopId`** is the arrival time after any wait; departure = arrival + `serviceMinutes`. `Route.totalMinutes` = arrival back at depot − `shiftStart` (drive + service + wait). Per-leg `driveMinutes` are integer-rounded for display; totals use unrounded values, so summing legs can differ from `totalMinutes` by a minute.
15. **Metrics**: `totalDistanceKm` = Σ route km, `totalMinutes` = Σ route minutes, `longestRouteMinutes` = max, `timeWindowViolations` = count of late stops. `stopsPerDriver` keyed by driver id.
16. **Baseline** (`baseline-round-robin-v1`) = stops in file order dealt round-robin to drivers, no sequencing, no capacity check (it represents "what dispatch does today"), scheduled with the same distance model as #10. Zero drivers → everything unassigned. On the seed: 355.4 km / 20 h 24 m / longest 9 h 25 m / 6 violations, versus 174.8 km / 17 h 31 m / 6 h 33 m / 0 after `nn-2opt-v1` (−51 % km, −14 % time).
17. **`computeMs`** is reported with one decimal (e.g. `44.1`), measured with `performance.now()`. The placeholder takes a few tens of milliseconds on the seed (~25–90 ms depending on machine and warm-up; ~3 ms without the idle-repair pass), well inside the 2 s budget.
18. `optimize()` and `baseline()` are pure, dependency-free TypeScript so they run identically in the Route Handler and in the browser (used as an offline fallback — see 22).

## API

19. `POST /api/optimize` validates with **zod 4**; unknown keys are stripped rather than rejected; invalid input → `400 { error, issues: [{ path, message }] }`; malformed JSON → `400` with an empty `issues` list; an optimizer exception → `500`. Because the endpoint is public and the placeholder is O(n²)–O(n³), the schema also **caps a request at 1000 stops and 50 drivers**, rejects **duplicate stop ids / duplicate driver ids** (issue path `stops` / `drivers`, message lists the offenders) and rejects a stop whose id is the reserved literal `"DEPOT"` (path `stops.<i>.id`). All three routes set `runtime = 'nodejs'` and `dynamic = 'force-dynamic'`; `/api/seed` and the optimize response send `Cache-Control: no-store`.
20. `/api/health` reports `version: '1.0.0'` (hard-coded; bump alongside `package.json`).

## State & persistence

21. Zustand store persisted under **`routeiq-v1`** (blob `version: 1`). Persisted: depot, drivers, stops (incl. statuses), routes, both metrics, algorithm, computeMs, lastOptimizedAt, activeDriverId, hiddenDriverIds. Not persisted: selectedStopId, toast, isOptimizing, optimizeError, hasHydrated. Version-0 blobs (an earlier build, straight-line km) are **migrated**: data, delivery progress and prefs are kept, the plan (routes/metrics/algorithm/computeMs/lastOptimizedAt) is dropped so the user re-optimizes once. Pages render skeletons until `useHasHydrated()` is true (avoids hydration mismatches); that hook reads a module-level flag set by `onRehydrateStorage` in **both** the success and the error branch, so a failed rehydration can never leave a page on its skeleton.
    - **Resilient storage.** The store uses a small custom `PersistStorage` instead of `createJSONStorage`: every `localStorage` access is wrapped in try/catch (Safari "block all cookies", sandboxed iframes, quota errors → the app runs in memory), an unparsable or mis-shaped blob is discarded with a `console.warn` and the app boots with defaults, and each persisted key is shape-checked on read (`pickPersisted`) so a bad `stops` value falls back to its default instead of crashing a selector.
    - **Write dedupe + cross-tab sync.** zustand re-serialises the persisted slice on *every* `set`, including ephemeral-only ones (toast, selection). The storage wrapper skips writes whose blob is byte-identical to what it last read/wrote/saw, so a dispatcher tab that only shows a toast never overwrites the progress a driver tab persisted meanwhile; and a `storage` event listener applies another tab's persisted slice (stops/routes/metrics/activeDriverId/hiddenDriverIds — never the ephemeral keys, never the hydration flag) straight into the open tab, so /dispatch and /driver on the same device stay consistent instead of clobbering each other.
22. **`optimize()` calls `POST /api/optimize`** (the swap seam) and only if that request fails or returns a malformed body does it fall back to the local `optimize()` with a `console.warn`. Baseline metrics are always computed locally (pure function). This keeps the demo working offline / behind a flaky network without hiding the API seam. The only callers are the **Optimize / Re-optimize routes** button on `/dispatch` and the **"Optimize now (demo)"** button on an un-optimized `/driver/[id]`; nothing else (not `resetDemo`, not a status change, not a page load) triggers the algorithm.
23. **Manual reassignment** (`moveStop`) rewrites the `driverId → stopIds[]` map and re-runs **only `schedule()`** — ETAs and metrics update synchronously; baseline metrics are left untouched (they are the "before"). It also works **before any optimisation**: the first move bootstraps an empty plan (every driver `[]`), so "Reassign to…" in a map popup creates a one-stop route while `algorithm` / `lastOptimizedAt` / `baselineMetrics` stay null. `moveStop` returns a boolean — `false` for a no-op (dropped where it already was), an unknown stop / driver or no depot — and every caller (map popup, ⋯ menu, drag-and-drop, unassigned list) toasts "Moved …" **only when it returns `true`**.
24. **Stop status changes do not re-plan.** Marking a stop delivered/failed only updates the stop; ETAs stay as planned. `deliveredAt` is set for both `delivered` and `failed` (attempt time) and cleared when reverted to `pending`.
25. **Failure reasons** are stored in the existing `notes` field as `"<reason> · <original notes>"` (no schema change); re-failing with another reason replaces the prefix instead of stacking. **Reverting to `pending` (undo) strips the reason prefix again** so a mis-tap leaves no trace and the Next Stop card never shows "No one home" as if it were a delivery instruction; while a stop is `failed` the driver's details sheet shows the reason as "Last attempt: …" and only the free-text remainder as notes.
26. `resetDemo()` re-fetches the seed (fresh statuses), clears routes/metrics/legend toggles, keeps `activeDriverId`, and does **not** re-optimize.

## Map

27. **Precomputed road paths (optional §4.4) were implemented.** `scripts/precompute-paths.ts` fetched, once, the OSRM demo-server driving polylines for all 1,035 unordered pairs of seed points and stored them Google-encoded in `src/data/paths.json` (~96 KB, loaded only by the lazily imported map chunk). The map uses them purely for **drawing**; distances/ETAs remain the haversine × 1.3 model (#10) so the optimizer contract stays independent of any external routing data — the km on screen are that road *estimate*, not the length of the drawn polyline. Paths are assumed symmetric (reversed for the opposite direction). The app never calls OSRM at runtime; if a pair is missing (e.g. a non-seed stop) the leg is drawn as a straight line.
28. Markers are Leaflet `divIcon`s (no image assets): 28 px coloured pins with the sequence number when routed (number colour picked by `onColor()` — slate-900 on the orange/green drivers, white on blue — so it always meets AA), amber/violet dots for priority/overnight, a green check for delivered, red X for failed, ring for selected; depot is a 32 px slate square. Route lines get a white halo for contrast, and small direction arrows on legs longer than ~700 m (≤ 60 arrows total). Zoom control sits top-right so the mobile bottom sheet never covers it; on phones the OSM attribution is CSS-ordered *above* the zoom bar in that corner so the opened legend never overlaps it. Attribution is the OSM-required string. A selected stop's popup pans into the part of the map not covered by the bottom sheet (`MapView.viewportInset`).
29. In the driver view the "current position" is the previous stop (or the depot before the first stop) — no geolocation is used (spec).

## Dispatcher UX

30. Mobile: full-screen map + bottom sheet with `peek` / `half` / `full` snaps (drag handle with a 44 px hit area, velocity-biased snapping, `100dvh`; the peek height and the header padding include `env(safe-area-inset-bottom)` so the Optimize button clears the home indicator, and the sheet body is `inert` while peeking so hidden rows are not in the tab order). Desktop (≥ 768 px): map left, panel right at `clamp(340px, 40vw, 460px)` so the map keeps ≥ ~56 % of a 768 px screen.
31. Cross-driver moves: **desktop** drag-and-drop with `@dnd-kit` (pointer + keyboard sensors; pointer drops use `pointerWithin`, so releasing over the map / header / a gap **cancels** instead of dropping on the nearest route, and dropping a row on its own card's padding is a cancel too; the insertion line is drawn above or below the hovered row from the pointer position and the drop uses the same side); **mobile** uses the per-row "⋯ → Move to Driver X" menu (spec: drag on a touch bottom sheet is fiddly; the menu measures itself after mounting and flips/scrolls so it never overlaps its trigger or leaves the viewport, and keyboard focus follows the moved row to its new card). The map popup also offers a "Reassign to…" select on both.
32. "Reset demo" uses an inline confirm (no `window.confirm`, which would block browser automation and looks off-brand). "Export routes (JSON)" downloads `{ exportedAt, depot, drivers, routes, metrics }`.
33. Legend (per-driver show/hide) is a collapsible chip on mobile so it doesn't crowd a 375 px map. Hidden drivers are shown struck-through in slate-500 (AA) rather than faded.
34. **Toasts are rendered per screen, not in the root layout.** `<Toast bottomOffset={…}>` sits in `DispatchScreen` (offset = the sheet's peek height on phones, so it floats above the Optimize strip) and in the driver screens (offset = the 56 px bottom bar), each adding `env(safe-area-inset-bottom)` itself. This keeps the landing page free of the store bundle and stops the toast covering the primary action.

## Driver UX

35. Failure reasons: `No one home` / `Wrong address` / `Damaged` / `Other`, chosen in a small modal sheet. "Navigate" opens the Google Maps directions deep link in a new tab (allowed by spec — no API key). "Return to depot" appears after the last stop and deep-links to the depot.
36. `/driver` remembers the last chosen driver (`activeDriverId`) and highlights it.
37. Driver sheets (stop details, failure reason) are **native `<dialog>` elements opened with `showModal()`** — top layer, background inert for pointer/keyboard/AT, Escape via the `cancel` event — with a `position: fixed` body scroll lock that survives iOS. After Delivered/Failed from the Next Stop card, keyboard focus moves to the new card's heading (or "Route complete") instead of dropping to `<body>`; the stop list deliberately does **not** auto-scroll on completion (the Next Stop card at the top is the source of truth). Done rows are dimmed by colour + strike-through rather than opacity so every text run stays ≥ 4.5:1.

## PWA

38. Manifest is generated by `src/app/manifest.ts` (served at `/manifest.webmanifest`); icons 192/512 (+ 180 apple-touch) are PNGs produced by `scripts/generate-icons.mjs` (`pnpm generate-icons`), a dependency-free Node script. The `purpose: 'any'` icons are the rounded slate square with transparent corners; the `purpose: 'maskable'` entries point at **dedicated `icon-maskable-192/512.png`** — full-bleed slate-900 square, artwork scaled into the central 80 % safe-zone circle (the script self-checks that the corner pixel is opaque and no foreground pixel lies beyond 40 % of the size), so Android squircle/circle masks never show notches or clip the route. `public/sw.js` is a minimal hand-written service worker: network-first for same-origin navigations with an inline offline fallback page; it never caches tiles or `/api/*`. It is registered only in production builds (`RegisterSW`).
39. Dark mode is not implemented (spec: not required); the scaffold's `prefers-color-scheme` block was removed so the map/cards never invert.

## Performance (Lighthouse mobile)

42. **What was done for load performance.** The Leaflet chunk (`MapViewInner`) is preloaded the moment a map page's JS evaluates (parallel with hydration and the `/api/seed` fetch); the map is created directly on its final bounds (`MapContainer bounds`, no throw-away default-zoom tiles); the 45 markers and polylines are streamed in with `useDeferredValue` (time-sliced transition, so the tiles paint before the marker commit); `<link rel="preconnect">` to `tile.openstreetmap.org`; no `Intl`/`toLocale*` calls on the hot path (the first `Intl.DateTimeFormat` cost ~180 ms on a mid-range profile — dates and clock times are hand-formatted); no synchronous layout reads during mount (header height comes from `ResizeObserver` entries, viewport height / safe-area inset are read in a `requestAnimationFrame` and via a `:root` custom property instead of a probe element); the map wrapper is `relative z-0 isolate` so Leaflet's z-indexes never trigger extra stacking work.
43. **Map loading placeholder is an image, deliberately.** While the Leaflet bundle loads, `MapSkeleton` shows `public/map-placeholder.webp` — a 6 KB, slate-toned, abstract silhouette of Madison's isthmus generated by `scripts/generate-map-placeholder.mjs` (SVG drawn procedurally, rasterised with a local Chrome; no OSM data). It reads as "a map is coming" instead of a grey block, ships in the server-rendered HTML with `fetchpriority="high"` + `decoding="sync"` so it joins the first paint, and — being the largest element on a phone — it is the page's Largest Contentful Paint candidate rather than a map tile that can only appear after Leaflet boots. A raster (not the SVG) is used because an SVG in an `<img>` is painted on the main thread, which is busy booting the app on slow devices. Preloading the first map tiles was tried and rejected: on a slow-4G budget the ~150 KB of tiles compete with the JS and make everything later.
44. **Measured numbers (honest caveat).** Lighthouse 12, mobile preset, against `pnpm build && pnpm start` on the Windows dev laptop that built this (Lighthouse itself warns *"The tested device appears to have a slower CPU than Lighthouse expects"*, benchmark index ≈ 650–900 vs the ≈ 1500 its 4× throttle assumes), medians of three runs: **landing** perf 89 / a11y 100 / best-practices 100 / SEO 100; **/driver/D1** perf 67 / a11y 100 / 100 / 100; **/dispatch** perf 54 / a11y 96 / 96 / 100 (accessibility 96 because Leaflet's 28 px stop markers overlap each other in dense clusters — the target-size audit — the same content is reachable from the panel list with 44 px rows). With the CPU multiplier calibrated to this machine per Lighthouse's own guidance (`--throttling.cpuSlowdownMultiplier=2`): landing 98, driver 79, dispatch 71. On `/dispatch` the remaining gap is the map itself: Lighthouse's Lantern model measures LCP from a localhost run in which the JS arrives with the HTML, so the first painted frame already contains the Leaflet map and the LCP becomes the first OSM tile (~4 s on simulated slow 4G); on a deployed origin the placeholder paints first. PWA installability (manifest with any + maskable icons, service worker in production, standalone display) is in place. Re-run locally with `pnpm dlx lighthouse http://localhost:3000/dispatch --form-factor=mobile --screenEmulation.mobile --chrome-flags=--headless=new`.
