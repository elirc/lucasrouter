Status: **not assessed**. Software checks do not fill this scorecard automatically.

| Dimension | 0 | 1 | 2 |
|---|---|---|---|
| Contract | Missing or contradictory | Mostly correct, examples incomplete | Explicit inputs/outcomes plus edge example |
| Mechanism | Incorrect or memorized | Correct explanation | Trace predicts a changed input correctly |
| Implementation | Missing important branch | Main contract works | Relevant edges and ownership preserved |

| Communication | Unclear or inflated | Understandable | Concise, factual, handles follow-ups |

Use the implementation dimension for an actual code artifact when the round requests one; otherwise mark it not applicable and report the denominator used. Do not silently award points for work a round did not require. An integration plan can be useful, but it is not executed evidence.

For a ten-point coding round, a practice target is eight with no zero in contract or mechanism. This is a self-study target, not a hiring threshold. For a four-dimension discussion round, report the score out of eight. Keep the individual dimensions visible so a polished explanation cannot hide a broken contract.

## Feedback that produces a next action

Replace vague feedback with a task. Instead of needs more React, ask the learner to distinguish a draft from incoming server data and trace a refresh while editing. Instead of improve testing, ask for an assertion that rejects the named shortcut. Instead of learn system design, ask where a concurrent second writer is prevented from violating the invariant.

Record both a strength and the first unsupported assumption. A good next session changes one input or boundary while keeping enough context to compare the two attempts. Repeating the answer verbatim tests memory; explaining a new counterexample tests transfer.
