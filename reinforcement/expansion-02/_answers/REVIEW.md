# Sealed capstone and review notes

Reject a whole-array rollback when the intended operation reverses one record: the unrelated-edit case demonstrates the data loss. Reject an unguarded token when intervening changes to the same record are possible. Do not insist on a version field if the real application's existing command identity and lifecycle already enforce the required rule; ask for evidence of that rule.

For keyboard work, require a product pattern before selecting key bindings. Arrow keys are appropriate for some composite widgets, not a universal replacement for normal Tab behavior. Native dialog modality and focus restoration remain separately verified. A screenshot cannot establish a correct focus sequence.

A strong capstone review separates restored domain fields, history semantics, offer lifetime, and focus behavior. Ask the learner to change one of those requirements and identify which layer and tests must change.

## Assess a learner's explanation

Ask for the actual input and observable result, then change one assumption. A strong explanation adapts the test or identifies a missing product decision. A weak explanation repeats the reference implementation without explaining why its boundary belongs there.

Do not award runtime evidence for a written plan. Keep “source supports this,” “model reproduced this,” and “application reproduced this” as separate statements. If an existing implementation already handles a scenario, the useful contribution may be a test and a clearer contract rather than another fix.
