# Several routes through the same idea: RouteIQ / lucasrouter

Choose a route based on what would help with today's problem. A preference is not a permanent label, and a fluent explanation in one format is not automatic evidence that you can use the idea in another. The routes below all return to the same fixture, rule, and observable result.

## Route A — Read and annotate, 45–60 minutes

Open one slow explanation and read only the setup and result first. Underline the values that identify the entity, scope, or operation. Write a prediction before reading why it follows. Then read the full explanation and mark the first sentence that changes or sharpens your initial reasoning.

Create a margin note for three distinctions: a fact supplied by the fixture, a policy chosen by the exercise, and a guarantee that would need application evidence. This prevents a long explanation from becoming a collection of facts that all appear equally established. Finish by rewriting the mechanism in six sentences and attaching one concrete counterexample to the tempting shortcut.

The useful output is an annotated example, not a page covered in highlighting. If you cannot explain why a highlighted sentence matters to the fixture, remove the highlight and replace it with a question about the relevant boundary.

## Route B — Trace and draw, 35–50 minutes

Choose a worked model and cover its result. Copy the starting state into a table. Add one row for each operation, event, or comparison, then predict the next state. Draw separate boxes for independent objects or records and shared arrows only where references or ownership justify them.

Compare your table with the solved trace. When they differ, identify the earliest divergence. Do not simply copy the final state into your table; explain the rule that changes the intermediate step. Then translate the trace into a small diagram with labeled arrows. The diagram should preserve the distinctions in the table rather than hiding several different relationships under one arrow style.

Apply the idea to dispatch list and driver dialog by locating one real caller and one real state owner. If the teaching model's fields do not exist in the app, write an explicit mapping or state that no direct mapping is established.

## Route C — Build and experiment, 45–75 minutes

Open the [worked notebook](WORKED-NOTEBOOK.md). Predict each example before running it. Run the provided command and compare the actual output checks with the written values. The notebook calls a separate existing teaching reference; it does not solve or overwrite your earlier starter exercise.

Make one additional fixture in a separate practice file. Change exactly one contract-relevant dimension, such as a duplicate ID, a boundary value, an omitted field, or an event order. Write the expected result before executing it. If it disagrees, decide whether the implementation, your prediction, or the assumed contract needs correction.

Finish by explaining which real boundary the model omits. In this project, start with the store action and its persistence boundary. A successful model run is useful evidence for its contract; it should not be reported as a browser, database, or provider test.

## Route D — Speak and listen, 25–40 minutes

Choose a solved case and explain it aloud without reading the answer. Use the user consequence first, then the mechanism. Name the values instead of relying on vague pronouns. A listener should know which record, scope, request, or version you mean at each step.

Ask a partner to change one input and predict the result together. If practicing alone, pause a recording or write the changed fixture before continuing. Do not judge the attempt by presentation polish alone. A halting explanation that correctly identifies the missing assumption can be more useful than a smooth answer that cannot handle a counterexample.

End with a short written note containing the strongest follow-up question and your revised rule. This connects speaking practice back to a durable artifact you can revisit.

## Route E — Reflect and reconstruct, 30–45 minutes

Read one fictional worked journal, then close it. Use [your own journal template](MY-JOURNAL.md) to record a real prediction you made while studying or coding. Keep the example small. You do not need a dramatic incident to describe a meaningful change in understanding.

Write what you thought would happen, why you thought it, what the trace or check showed, and what rule you now use. Separate an observed result from a plan to verify it later. If you received a hint or read a reference, say so. That information helps choose the next exercise rather than diminishing the value of the attempt.

## Combine routes without multiplying work

A useful combined session is ten minutes of prediction, fifteen minutes of tracing, fifteen minutes of explanation, and ten minutes of reflection. Do not run all five routes every time. Use a second format when the first leaves an important uncertainty unresolved.

For RouteIQ / lucasrouter, begin with one of the six local cases, then choose one related worked model. The model teaches a mechanism in a small setting; the local case asks how that mechanism relates to actual ownership and scope. If the connection is weak, state the difference rather than forcing a pattern match.

## When to stop a session

Stop when you can predict a changed fixture, explain the decisive step, and name the next unverified boundary. If you are only rereading familiar prose, switch to retrieval or a new example. If application setup blocks progress, preserve the exact proposed check and continue with source tracing without marking runtime verification complete.
