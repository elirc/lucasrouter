# Slow explanation 04: Proof and status disagree

This page retells the case as a fully worked reasoning exercise. It can be read before the [journal](../journals/04.md), afterward as a compact explanation, or beside the [workshop](../workshops/04.md). The goal is to understand why the result follows, not to memorize one patch.

## 1. Translate the situation into a contract

A report says a stop is delivered while its required proof field is absent. The candidate must distinguish UI form validation from the domain transition and historical-data policy.

The concrete fixture is **Synthetic rule: delivered requires proofId; input {status:delivered,proofId:null}.**. The governing rule is **A transition must satisfy the chosen status-and-proof contract at its authority boundary.**. These sentences play different roles. The fixture describes one input or timeline. The rule describes what must remain true across inputs. A correct explanation uses the rule to derive the result for the fixture; it does not infer a universal rule from one convenient example.

The user wants to record a delivery outcome. The relevant interface is the dispatch list and driver dialog, but the interface may not own the authoritative decision. Track route and driver identity while following the path to the store action and its persistence boundary. If one of those boundaries is absent from the particular local interaction, mark it absent rather than drawing a fictional server call.

## 2. State the worked result explicitly

Reject this synthetic transition with a useful field error. Inspect delivery validation to determine the actual application policy; do not infer that every delivery requires the same proof type.

This is the expected reasoning under the teaching contract. It is not a claim that a live application was exercised during this explanation. To make an application claim, inspect the current source and run the appropriate focused check. The distinction lets us use a small example to understand a mechanism without exaggerating what the example proves.

## 3. Find the exact failure in the tempting approach

The tempting approach is: **Disable a button and assume all other callers are now validated.**

The important question is where that approach loses information needed by the rule. It may merge values that should remain distinct, treat arrival order as authoritative order, use a visible position as identity, or accept a decision from the wrong owner. Name the relevant loss in this fixture. Do not substitute a general statement such as state is hard or async is tricky.

Once the loss is visible, the repair becomes easier to bound. Restore the missing distinction at the first boundary that needs it. If a response needs current request identity, checking only at launch is too early. If a server operation needs authorization, changing a button is too late or too weak. If a group invariant needs its composite key, a global total has already discarded the distinction. Use the case's actual mechanism rather than assuming every example requires every one of these repairs.

## 4. Preserve the parts that were already correct

A focused correction should not erase unrelated records, discard a newer draft, change an old caller's field meaning, or rewrite a transaction that already has the intended boundary. The correct unaffected state depends on this case. Name it before editing so the acceptance test has something concrete to protect.

This is why a before/after table should include preserved values. A patch can make the main assertion pass by clearing everything, refusing every request, or returning an empty result. Those approaches may remove the symptom while violating the user's original operation. A second assertion about useful behavior distinguishes a real correction from a blanket shutdown.

The same principle applies to curriculum work. If the repository already contains the correct behavior, the learning task is to explain and characterize it. There is no need to manufacture an application edit merely to make the exercise feel like implementation work.

## 5. Separate four kinds of evidence

**A prediction** is what the rule implies before execution. It is valuable because it can be compared with an observation. **A source trace** identifies the actual symbols and branches that appear to enforce the rule. It can reveal missing scope or a wrong owner, but it does not exercise every runtime dependency.

**A teaching-model check** executes the small stated contract with controlled inputs. It can establish the table's arithmetic or transition policy while leaving persistence, browser behavior, and external services outside its scope. **An application check** reaches the actual boundary named in the claim. Its fixture, environment, assertions, and remaining limitations should be recorded.

The four forms support one another. They should not be relabeled as equivalent just to make a checklist look complete. In particular, reading a sealed answer or running the author's reference does not demonstrate that a learner can reproduce the reasoning independently.

## 6. Work a counterexample carefully

Keep the original fixture visible. Change one dimension that matters to its rule: identity, ordering, field presence, scope, revision, or failure point. First predict whether the outcome should change. Then identify the branch or boundary responsible. If changing a dimension has no effect, explain why it is irrelevant under this contract rather than forcing a different answer.

A good counterexample is small enough that a teammate can reproduce it. It does not need production-scale data. Two records can expose a scope or aliasing problem. Two overlapping operations can expose stale application. One late failure can expose a rollback boundary. Larger fixtures may be useful later, but they should not obscure the first mechanism you are trying to understand.

## 7. Explain the tradeoff without overselling a tool

The corrected rule can often be implemented in more than one way. Compare them by preserved behavior, complexity, compatibility, and testability. A familiar library or pattern is not a reason by itself. Nor is fewer lines automatically better if those lines collapse important outcomes.

State which stronger guarantees are outside the teaching model. A serial allocator does not become an atomic inventory service. A deterministic selector does not claim work. A runtime schema does not prove factual truth. A response gate does not implement durable idempotency. Pick the limitation actually relevant to this case and connect it to the next verification boundary.

## 8. A plain-language explanation to retain

Begin with the user and fixture, state the rule, identify why the shortcut violates it, and describe the corrected result. Then add one preserved behavior and one remaining evidence limit. This produces an explanation that a teammate can challenge with a changed input, which is more useful than a slogan that cannot be tested.

Return to the [project source map](../README.md) and annotate one real path using this structure. Keep proposed behavior, existing behavior, and your own observed result distinct. The explanation is complete when the reader can follow the decision and its limits, not when every neighboring feature has been discussed.
