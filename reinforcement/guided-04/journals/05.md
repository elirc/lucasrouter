# Worked learning journal 05: Keyboard focus loses its owner

**Format note:** this is a fictional learner's narrated reasoning, written as a teaching example. It is not the user's diary, an actual incident report, or a claim that application changes were made. The fixture and expected policy are synthetic unless the source notes explicitly identify existing behavior. Executed checks belong to the separate validation report.

## Entry 1 — I start with the user's situation

Today I am studying a delivery stop problem. The user is a dispatcher or driver, and the part of the interface I can point to is the dispatch list and driver dialog. That description is already more useful than saying I am learning the whole stack. It gives me a person, a visible surface, and a bounded operation: record a delivery outcome.

The situation is this: A driver opens a dialog, its opener is removed by a list update, and the dialog closes. The exercise concerns a sensible fallback and observable keyboard behavior.

My first impulse is to search for a familiar pattern and start editing. I pause because a pattern name can conceal the missing requirement. I need to know what result would count as correct for this particular input. Otherwise I can make the code shorter, add a hook, or introduce a helper without resolving the thing the user would actually notice.

## Entry 2 — I write down the facts before the explanation

The starting fixture is: **Opener S1 disappears while dialog is open; user presses Escape.**

I copy those values onto a separate line and resist adding convenient facts. I have not established that every input is trusted, that only one caller exists, that every response arrives in launch order, or that all effects share a transaction. If the small model assumes one of those things, I will label it. If the application needs to prove one of them, I will locate its owner.

This separation helps because I often confuse a fact in the prompt with a conclusion I supplied myself. For example, a successful response tells me something about a request, but it may not tell me that the response belongs to the current selection. A copied outer object tells me an identity changed, but not that all nested identities changed. The exact misleading inference depends on the case; writing the fixture first keeps me from skipping that step.

## Entry 3 — My tempting first prediction

The shortcut I am deliberately examining is: **Choose an arbitrary DOM node or assert focus behavior with only an array unit test.**

I can see why someone might reach for it. It reduces the number of things to track and can work on an uncomplicated happy path. That makes it a useful learning example rather than an absurd straw person. I want to find the smallest input for which the shortcut stops satisfying the intended behavior, not merely repeat that the preferred pattern is better.

I keep the original prediction in my notes instead of replacing it with the answer. Later, the difference between my prediction and the worked result will show what I learned. If I overwrite the first note, the page will look polished but will no longer reveal the assumption that changed.

## Entry 4 — I choose the rule that must survive

The invariant for this case is: **Closing a dialog should leave focus at a meaningful available control.**

I read it slowly and ask which words describe identity, which describe timing, and which describe authority. A rule about the current record is not automatically a rule about the first record in an array. A rule about an accepted command is not automatically a rule about every delivered request. A rule about a user's visible draft is not automatically a rule about the last fetched object.

The boundary I will investigate is the store action and its persistence boundary. That is a source-reading target, not yet proof. I need to find the current caller and follow the data through it. If the small exercise introduces a revision, status, or field that the application does not have, I will explain the difference instead of attributing the model's guarantee to the repository.

## Entry 5 — I reconstruct the example on paper

I make a table with before, input or event, decision, after, and unaffected state. The starting fixture goes in the first two columns. The invariant tells me which decisions are allowed. The unaffected-state column is important because a change can produce the desired visible value while damaging something else.

The worked resolution is: **Use the current native-dialog behavior as the starting point, then specify a surviving fallback. Verify keyboard order in a browser; a pure next-target function cannot prove actual focus movement.**

I now compare that resolution with the tempting shortcut. I am looking for the first divergence, not the last visible symptom. If the wrong identity is selected early, a later render may look broken even though it renders the supplied data accurately. If an unauthorized field crosses a server boundary, hiding it later does not remove the earlier exposure. If a transaction boundary is incomplete, a friendly error message does not undo a persisted side effect.

## Entry 6 — I separate a policy choice from a coding mistake

Some details in an exercise are deliberately chosen policies. The application could choose a different missing-selection behavior, conflict response, normalization rule, or late-event reconciliation policy. A different policy is not automatically a programming error. It becomes an error when implementation and stated contract disagree, or when a stronger guarantee is claimed without evidence.

For this case, I retain the stated invariant while checking which details are fixed and which require a product decision. I can propose another coherent rule, but then I must update the examples and explain its user consequence. I cannot silently switch rules halfway through the trace because the alternative makes my code easier to write.

This is also where I avoid overgeneralizing. A local teaching model may serialize calls, accept already validated records, or omit a persistence layer. Those simplifications are useful when named. They become misleading only when I carry the result into a stronger claim about the whole application without restoring the missing boundary.

## Entry 7 — I explain the correction without a slogan

My revised explanation begins with the fixture and the rule, not with use a Map, add a transaction, or put it in an effect. Those tools might be appropriate, but the listener needs to know what they preserve. I explain which value or event owns the decision and why the tempting shortcut applies the wrong equivalence, order, or authority.

I use a short before-and-after account. Before the correction, the shortcut can produce a result inconsistent with the invariant. After the correction, the decision is made at the boundary that has the required information. I then name an unrelated record, earlier valid result, or existing user input that should remain unchanged. That makes the repair bounded rather than an excuse to redesign every surrounding feature.

The exact implementation may vary. Two functions can have different loops and still satisfy the same contract. My explanation should survive that variation. If I can only defend the line-by-line spelling of one answer, I have memorized a solution rather than understood the mechanism.

## Entry 8 — A mentor asks what my test would prove

**Mentor:** What result would reject your first shortcut?

**Learner:** I would use the supplied fixture and assert the specific outcome implied by the invariant. I would also check the unrelated state that should stay unchanged. An assertion that something succeeded, returned an array, or displayed a row is too weak when the issue is which entity, version, or scope is involved.

**Mentor:** Would that prove the application is fixed?

**Learner:** Only if the test reaches the boundary where the application guarantee lives. A pure function can prove its written input/output policy. It cannot by itself prove keyboard focus, a real query predicate, transaction rollback, durable deduplication, or an external provider's final result. I would label those additional checks separately.

**Mentor:** What if the current implementation already handles the case?

**Learner:** Then the useful work may be a source trace, characterization test, or clearer explanation. I should not invent a defect merely because the curriculum gives me a failure scenario to reason about.

## Entry 9 — I design the smallest useful observation

I want an observation that distinguishes explanations. I write two competing hypotheses and predict what would differ if each were true. The exercise's shortcut supplies one plausible mechanism; an adapter or presentation issue can supply another when appropriate. I avoid claiming either is confirmed until I have an observation at the right boundary.

For timing, I prefer a controlled event order to a long sleep. For data identity, I include a second record or scope. For a write, I inspect the durable or returned state that matters, not just the number of mocked calls. For a UI interaction, I describe what the user can actually see or operate. The method changes with the guarantee, which is why there is no single test style that substitutes for all the others.

I also identify one test that could pass while the defect remained. That question is uncomfortable but useful. It forces me to inspect whether my mock, fixture, or assertion has already assumed the property I want the implementation to demonstrate.

## Entry 10 — I translate the same reasoning into another form

First I redraw the trace as boxes and arrows. Boxes stand for values or owners; arrows stand for one named relationship at a time. I do not use the same unlabeled arrow for an object reference, an HTTP request, and a transaction boundary. The drawing is useful only when its symbols mean something precise.

Then I explain the case aloud as if a teammate has not read the code. I name the user, the input, the invariant, the wrong turn, and the corrected result. If I need a technical term, I connect it to the consequence immediately. Finally I write the short version beside the drawing. Moving between these forms shows whether my understanding depends on copying the wording from one paragraph.

## Entry 11 — I leave an honest evidence record

My notebook has separate labels for predicted, traced in source, executed in a teaching model, and observed in the application. In this fictional worked entry, the reasoning is a teaching demonstration. The repository's actual verification report is the place to look for executed author checks. My own learning would still need an independent attempt.

I do not borrow the authorship of existing project code, and I do not turn a proposed experiment into a completed result. If I later use this example in an interview, I can accurately describe what I studied, what I implemented in a lab, and what I personally verified. That is enough to have a useful technical conversation without manufacturing a production incident.
